# iOS 自定义键盘启动时延：冻结实测基线（2026-10-15）

## 最新事实：录屏优先于肉眼判断

用户逐帧复核发现：万象方案助手也显示启动转圈，不过持续时间很短，系统键盘完全展开时脚本界面已经显示。因此先前“万象从不转圈”的判断错误。Rime 0.3.57、完整依赖且最小 UI 的 A、仅三个文件最小 UI 的 B 均转圈；先前“A 不转”的判断也错误。

现有事实只支持万象在用户录屏中具有更短的感知等待；未收到录屏文件本身、尚未给出帧差或毫秒。不可将静态依赖、UI 树、原生工具栏、请求高度或 Rime 引擎直接称为已证明的原因。

## 唯一有效的三个时间点

- T0：从 Scripting 外部的系统输入法触发切换至 Scripting 的视频可见时刻，不是 Scripting 内部换脚本。
- T1：目标脚本 UI 第一次出现在键盘区域的画面帧，T1 - T0 是可见启动时间。
- T2：目标脚本可被按键操作并在宿主输入框显示输入的时刻，T2 - T0 是输入就绪时间；包含用户点击反应时延，标明这一限制。

补充记录：系统键盘容器展开结束的帧、转圈首次出现与结束的帧。利用真实录屏帧率计算帧差；录屏帧率及事件选帧误差要保留，不把 JS 计时替代视频第一帧。

## 对照要求和结论边界

比较万象与 Rime 时保持相同设备、系统输入框、节能模式、环境负载/温度、唤起路径，至少 3-5 次有效外部唤起后比较中位帧差。系统可能重用扩展进程，重新打开输入框不保证是真正冷启动；不能把每次重开直接标为“冷启动”。

现有 0.3.57 的 JS trace 仅从 main() 执行开始。ui.present.return / ui.root.hooksReady / ui.effect.begin / rime.runtimeReady 不代表首帧。过去约 36-37 ms 的 JS 结果不能用来解释系统级转圈时长，也不能证明 Rime 已达到与万象一致的用户体感。

尚未提供视频原件，无法在本轮计算 Wanxiang 与 Rime 的 T1、T2 中位数、P50/P95，不应推测绝对耗时。已有 A/B 两份冻结安装包只是历史对照，不需要再重复只判断转圈有无的二元实验。

## 下一步版本契约

首先定量分析视频中的 T0 / T1 / T2 与键盘展开时刻。若 Rime 的差异集中在 T1 之前，再围绕入口加载、同步设置读取、首次视图创建进行单因素对照；若 T1 接近但 T2 较慢，才优先针对 Rime Session、输入能力初始化进行调整。

必须维持九键/26 键、中文/英文、候选、手势、输入区域和布局不回归。不得在没有视频验证时宣称性能收益。不得修改正式 main 或覆盖现有 0.3.57 latest.zip、0.3.46 兼容别名、冻结 0.1.0 A/B 包。

取消尚未发布的 W/T/H 原生键盘选项三组合安装包计划：此前只改变 toolbar 与 requestHeight 测量有无转圈，不能回答现在的连续时间优化目标。决策在此留痕，防止未来回归相同的无效实验。

## 下轮工作入口

用户已经录制万象助手视频，不再要求重复验证“是否转圈”。先利用现有视频确定 T0、T1 和容器展开结束帧，并与 Rime 视频对照；只有差异被定量证明后，才针对首帧前的真实瓶颈提出小范围代码改动。
